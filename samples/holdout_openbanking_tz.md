# Техническое задание: Open API банка для партнёров

**Заказчик:** Департамент цифрового бизнеса АО «Жетысу Финанс Банк»
**Версия:** 0.9 (черновик для согласования), 12.11.2026
**Подготовил:** бизнес-аналитик управления партнёрских интеграций

## 1. Цели проекта

Банк открывает API для финтех-компаний и агрегаторов счетов, чтобы клиенты могли с их согласия делиться выписками и инициировать платежи из сторонних приложений. Ожидаемые результаты на первый год после запуска:
- подключить не менее 15 партнёров;
- набрать 200 000 активных согласий клиентов к концу 2027 года;
- сократить срок технической интеграции партнёра с 3 месяцев до 3 недель.

## 2. Границы проекта

Входит: портал разработчика, регистрация партнёров, сервис согласий, API счетов и выписок, API инициирования платежей, вебхуки, тестовая песочница.
Не входит: карточные операции, кредитные продукты, переводы за рубеж, доработки мобильного приложения банка (ведутся отдельным проектом).

## 3. Роли и термины

- **Партнёр (TPP)** — юрлицо, прошедшее проверку банка и заключившее договор на использование Open API.
- **Клиент** — физлицо или ИП, обслуживающийся в банке и выдающий согласие партнёру.
- **Согласие** — разрешение клиента на доступ партнёра к определённым данным или операциям на ограниченный срок.
- **Администратор партнёров** — сотрудник банка, который рассматривает заявки и управляет доступом партнёров.
- **АБС** — автоматизированная банковская система; **ДБО** — интернет-банкинг банка.

## 4. Функциональные требования

### 4.1. Регистрация партнёров

**FR-01.** Партнёр подаёт заявку на портале разработчика: БИН, сведения о лицензии АРРФР (если деятельность лицензируется), контактные лица, описание продукта, запрашиваемые scope.
**FR-02.** Администратор партнёров рассматривает заявку в течение 5 рабочих дней; проверку контрагента по санкционным перечням и наличие лицензии подтверждает служба комплаенс.
**FR-03.** После одобрения система генерирует client_id и client_secret и отправляет их контактному лицу партнёра на e-mail открытым текстом, чтобы партнёр мог сразу начать подключение.
**FR-04.** Для продуктивной среды партнёр загружает на портал сертификат для mTLS, выпущенный аккредитованным удостоверяющим центром.

### 4.2. Авторизация и согласия клиентов

**FR-05.** Авторизация реализуется по OAuth 2.0 (authorization code + PKCE). Клиент перенаправляется на страницу банка, входит в ДБО и подтверждает согласие одноразовым кодом из SMS или push-уведомлением.
**FR-06.** На экране согласия отображаются: наименование партнёра, перечень передаваемых данных или операций, счета, срок действия. Клиент может исключить отдельные счета.
**FR-07.** Согласие на доступ к выпискам действует 90 календарных дней, после чего клиент подтверждает его заново.
**FR-08.** Access-токен действует 5 минут; refresh-токен выдаётся бессрочно и не меняется при использовании, чтобы партнёру не приходилось заново проводить клиента через авторизацию.
**FR-09.** Для партнёров категории «доверенный» (более 50 000 активных пользователей) допускается упрощённое оформление согласия: партнёр передаёт банку ИИН и номер телефона клиента, и согласие считается выданным без входа клиента в ДБО.
**FR-10.** Клиент видит список выданных согласий в ДБО и может отозвать любое из них одним действием.
**FR-11.** Отзыв согласия вступает в силу немедленно: все токены, выданные по этому согласию, аннулируются, последующие вызовы API возвращают 401.

### 4.3. Счета и выписки

**FR-12.** API возвращает список счетов, входящих в согласие: маскированный IBAN (последние 4 символа), валюту, тип счёта и текущий остаток.
**FR-13.** Выписка доступна за период до 24 месяцев от текущей даты, постранично — не более 500 операций на страницу.
**FR-14.** Суммы во всех ответах передаются целым числом в тиынах (минимальных единицах валюты) вместе с кодом валюты по ISO 4217.
**FR-15.** После отзыва согласия партнёр сохраняет доступ к выпискам через API до конца текущего календарного месяца, чтобы корректно завершить расчёты в своём продукте.

### 4.4. Инициирование платежей

**FR-16.** Партнёр создаёт платёж между счетами клиента или в пользу третьего лица внутри РК в тенге. Банк присваивает платежу paymentId и возвращает статус `PENDING_AUTHORIZATION`.
**FR-17.** Клиент подтверждает платёж на стороне банка: на экране показываются сумма, получатель и комиссия, код подтверждения привязан к сумме и получателю.
**FR-18.** Если после подтверждения клиентом партнёру нужно скорректировать платёж, он может изменить сумму и реквизиты получателя без повторного подтверждения, если отклонение суммы не превышает 10%.
**FR-19.** Статусы платежа: `PENDING_AUTHORIZATION`, `ACCEPTED`, `EXECUTED`, `REJECTED`, `CANCELLED`. При таймауте ответа АБС платёж остаётся в статусе `ACCEPTED` до получения окончательного ответа, клиенту и партнёру отказ не возвращается.
**FR-20.** Максимальная сумма одного платежа через Open API — 1 000 000 тенге, суточный лимит на клиента по всем партнёрам — 3 000 000 тенге.
**FR-21.** Размер комиссии за платёж через партнёра и порядок её отображения клиенту — TBD, ждём решения тарифного комитета.
**FR-22.** Контроль ПОД/ФТ по инициированным платежам выполняется банком в штатном порядке; причины отказа по ПОД/ФТ партнёру не раскрываются, возвращается обобщённый статус `REJECTED`.

### 4.5. Вебхуки

**FR-23.** Банк отправляет партнёру вебхуки о смене статуса платежа и об отзыве согласия. Тело вебхука содержит только тип события и идентификатор объекта; детали партнёр получает вызовом API.
**FR-24.** Вебхуки доставляются по HTTP или HTTPS на выбор партнёра; подпись сообщения и проверка сертификата не требуются — партнёр сам отсекает чужие события по IP-адресу отправителя.
**FR-25.** При неуспешной доставке выполняется до 5 попыток с интервалами 1, 5, 15, 60 и 240 минут.

### 4.6. Тестовая песочница

**FR-26.** Песочница изолирована от продуктивного контура и содержит только синтетические данные; тестовые client_id, client_secret и счета публикуются в документации и одинаковы для всех разработчиков.
**FR-27.** Песочница эмулирует все методы продуктивного API, включая ошибки и таймауты АБС, по заранее описанным тестовым сценариям.

## 5. Нефункциональные требования

**NFR-01.** Время ответа API (95-й перцентиль): не более 800 мс для запросов счетов и статусов, не более 2 с для создания платежа.
**NFR-02.** Система должна выдерживать пиковые нагрузки и масштабироваться по мере роста числа партнёров.
**NFR-03.** Ограничение частоты запросов — 100 запросов в секунду на одного партнёра; при превышении возвращается код 429.
**NFR-04.** Доступность продуктивного API — не ниже 99,9% в месяц.
**NFR-05.** Вызовы API в продуктивной среде принимаются только по TLS 1.2+ с mTLS.
**NFR-06.** Данные клиентов и согласий хранятся в ЦОД банка на территории РК; токены и client_secret хранятся только в виде хэшей.
**NFR-07.** Портал разработчика должен быть удобным и интуитивно понятным для партнёров.
**NFR-08.** Шифрование данных на уровне хранилища и управление ключами — требования уточняются с ДИБ.

## 6. SLA для партнёров

| Параметр | Значение |
|---|---|
| Доступность продуктивного API | 99,5% в месяц |
| Доступность песочницы | 99% в рабочие часы |
| Лимит запросов на партнёра | 50 запросов в секунду |
| Срок действия согласия на выписки | 180 дней |
| Максимальная сумма одного платежа | 1 000 000 тенге |
| RTO / RPO | 4 часа / 15 минут |

Плановые работы проводятся с 02:00 до 05:00 по времени Астаны; партнёров оповещают через портал не позднее чем за 3 рабочих дня.

## 7. Интеграции

- АБС — остатки, выписки, проведение платежей (через внутреннюю шину).
- ДБО — аутентификация клиента, подтверждение согласий и платежей.
- SMS-шлюз и push-сервис — одноразовые коды.
- Комплаенс-система — проверка партнёров при регистрации.

## 8. Эксплуатация и поддержка

Поддержка партнёров — через портал и e-mail, время первичного ответа — 4 рабочих часа. Метрики API (число вызовов, ошибки, задержки) выводятся в систему мониторинга банка. Документация публикуется на портале в формате OpenAPI 3.0.

## 9. Этапы и сроки

- Этап 1 (до 31.03.2027): регистрация партнёров, согласия, выписки, песочница.
- Этап 2 (до 30.06.2027): инициирование платежей, вебхуки.
- Пилот с 3 партнёрами — апрель 2027 года.

## 10. Риски и допущения

- Партнёры самостоятельно получают необходимые лицензии АРРФР; банк не отвечает за их продукты.
- Рост нагрузки на АБС из-за запросов выписок; при необходимости вводится кэширование остатков.
