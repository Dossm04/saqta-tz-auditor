# Питч и защита: Saqta TZ Auditor

Кейс BCC-HUB «AI requirements validator»: статическое ревью документа с требованиями по ISO/IEC/IEEE 29148:2018
(§5.2.5 и §5.2.6) и IEEE 830 §4.3. Сценарий на 5 минут, сценарий видео-демо и ответы на вопросы жюри.
Номинации: Best Business Value, Best Architecture, Best Presentation.

## 0. Подготовка (за 10 минут до выступления)

- В `.env` лежит `GEMINI_API_KEY` (см. README). Без сети используйте `--offline` или провайдер «Офлайн-правила» в UI.
- Прогоните кейс один раз заранее: ответы LLM попадут в кэш `.cache/llm`, и на сцене прогон будет быстрым и повторяемым.
  ```
  python validate.py examples/case_requirements.pdf reports/requirements_report.md
  ```
- Откройте во вкладках: `reports/requirements_report.md`, `streamlit run app.py` (режим «ISO-ревью требований»),
  README с таблицей метрик.

## 1. Боль — 30 секунд

> Ошибка в требованиях, найденная на ревью, исправляется правкой строки. Та же ошибка в проде становится инцидентом.
> Типовые беды документа: противоречия между разделами, непроверяемые формулировки («быстро», «при необходимости»)
> и пропуски (код ответа упомянут, но не описан). Ручное ревью по ISO 29148 занимает часы и зависит от человека.

## 2. Живое демо — 2 минуты

1. **Терминал**: `python validate.py examples/case_requirements.pdf reports/report.md`. Агенты отчитываются по шагам:
   сегментатор, правила, три LLM-критика параллельно, верификатор цитат, вердикт.
2. **Отчёт** (`reports/report.md`), идём по разделам:
   - паспорт прогона: документ, дата, модель, версия и коммит агента;
   - нарезка: 54 требования, «ID в отчёте — ID в документе — формулировка»;
   - находка-противоречие: **Ф-2 против критерия приёмки 2, январь против февраля**, с цитатами и строками;
   - находки по API: **GET для сохранения**, **200 + ERROR вместо 400**, **нет метода чтения**, **201/404 не описаны**;
   - сводка: 61 замечание, критичные отдельно (непроверяемые, противоречивые, неполные);
   - вердикт: **начинать разработку нельзя**, и список того, что исправить первым.
3. **Веб-интерфейс**: загрузка того же PDF, живые карточки агентов, вкладки «Нарезка требований», «Проверка набора»,
   «Вопросы автору».

## 3. Архитектура — 1 минута

- Восемь агентов: Сегментатор → Правила → (Критик требований ‖ Критик набора ‖ Охотник за противоречиями ‖
  Доменный критик) → Верификатор цитат → Вердикт.
- **Доменный критик** знает, где в платёжных требованиях прячутся дефекты: часовой пояс и момент операции
  (совершение или проведение), тиыны против тенге, повторная доставка без ключа идемпотентности, возвраты против
  уведомлений по порогу, НФТ без перцентиля и нагрузки, хранение данных без срока, правила без критериев приёмки.
  Работает и на правилах (офлайн), и через LLM.
- **Сегментатор** разбирает PDF со структурой: заголовки по размеру шрифта, таблицы (в том числе разорванные между
  страницами), блоки кода. У каждого требования есть номер строки и страница.
- **Верификатор цитат** защищает от галлюцинаций: каждая цитата LLM ищется в тексте документа, неподтверждённые
  замечания отбрасываются. Статус «дефект» без объяснения понижается до предупреждения.
- **Гибрид правила + LLM**: правила находят очевидное (TBD, размытые слова, НФТ без меры, незаполненные разделы
  шаблона), LLM находит смысловые противоречия. Если модель недоступна, агент перебирает запасные модели Gemini,
  затем работает на правилах. Демо не падает.

## 4. Ценность и доказательства — 1 минута

- **Документ кейса**: заранее вручную размечено 24 дефекта (`eval/iso/case_requirements.json`).
  С LLM агент находит **23/24 (96%)**, офлайн на правилах **22/24 (92%)**. До доменного критика было 19/24 и 10/24.
  Проверка: `python scripts/eval_iso.py --llm`.
- **Честность метрик**: доменные правила написаны после разбора пропусков на этом документе, поэтому офлайн-цифра на нём
  оптимистична. Мы проверили, что правила не шумят на 12 других ТЗ (на эталонном ТЗ — ноль замечаний). Независимая цифра —
  слепая выборка: правила **50%**, с LLM **67%**.
- **Что пропускает**: противоречие Ф-3 «максимум один push в месяц» и Ф-4 «push независимо от истории» ловится
  не в каждом прогоне.
- **Готовность к банку**: маскирование ПДн до отправки в LLM, возможность локальной модели, секреты только в `.env`,
  CI с прогоном на документе кейса на каждый коммит.

## 5. Сценарий видео-демо (2–3 минуты, для сдачи 27.11)

1. 0:00–0:15. Титул: Saqta TZ Auditor, кейс BCC-HUB, команда Saqta Labs.
2. 0:15–0:45. Терминал: одна команда `validate.py` на PDF кейса, видно ход агентов и путь к отчёту.
3. 0:45–1:45. Отчёт: паспорт → нарезка → противоречие Ф-2 → находки по API → сводка → вердикт.
4. 1:45–2:30. Streamlit: загрузка PDF, карточки агентов, вкладки отчёта.
5. 2:30–2:50. Метрики 23/24 и честная слепая выборка, ссылка на репозиторий.

Записывать удобно встроенным в Windows **Win + Alt + R** (Xbox Game Bar) или OBS. Перед записью прогоните кейс
один раз, чтобы ответы были в кэше и видео не ждало сеть.

## 6. Ответы на вопросы жюри

| Вопрос | Ответ |
|---|---|
| Чем это лучше одного промпта к ChatGPT? | Узкие роли и проверяемый вывод: каждое замечание с цитатой и строкой, верификатор отсекает выдумки, есть офлайн-режим и воспроизводимость через кэш. Один промпт не даёт ни полноты по характеристикам стандарта, ни гарантии, что цитата существует. |
| Как вы боретесь с галлюцинациями? | Нечёткий поиск каждой цитаты в документе, порог совпадения, отсев неподтверждённых замечаний, понижение статуса без объяснения. |
| А если LLM недоступен? | Ротация на запасные модели при 429/503/404, затем откат на правила. Отчёт той же структуры. |
| Можно ли отправлять документы банка во внешний LLM? | Можно подключить локальную модель (OpenAI-совместимый endpoint, например Ollama). Для облака ПДн маскируются до отправки (docs/PRIVACY.md). |
| Как измеряли качество? | Экспертная разметка 24 дефектов документа кейса и слепая отложенная выборка, написанная без доступа к правилам. CI прогоняет eval на каждый push. |
| Почему не 100%? | Тонкие смысловые противоречия между правилами (Ф-3 и Ф-4) LLM находит не в каждом прогоне. Доменные пробелы (часовые пояса, единицы сумм, идемпотентность, возвраты) закрыл Доменный критик. |
| Не подогнаны ли правила под документ кейса? | Доменные правила появились после разбора пропусков, это честно указано. Поэтому мы прогнали их на 12 других ТЗ и закрепили тестами отсутствие шума; независимая оценка — слепая выборка. |
| Как встроить в процесс? | CLI для пайплайна (`validate.py`, JSON-отчёт через `--json`), веб-интерфейс для аналитика, Docker-образ. |
