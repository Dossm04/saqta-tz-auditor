# Режим конфиденциальности: ТЗ банка не уходит наружу в открытом виде

Банк не отправит во внешнюю LLM ТЗ с реальными ИИН, номерами карт и контактами сотрудников. Поэтому в Saqta TZ Auditor есть три режима работы, и их можно менять, не трогая код.

| Режим | Куда уходит текст ТЗ | Когда выбирать |
|---|---|---|
| **Офлайн-правила** | Никуда. Проверку делают детерминированные правила базы знаний | Если нельзя передавать данные совсем, демо без сети |
| **Локальная модель (Ollama / vLLM)** | Только на сервер внутри контура банка (`localhost`, внутренняя сеть) | Основной режим для промышленного использования |
| **Облако (Gemini, OpenAI, shai.pro)** | Внешнему провайдеру, но **только после маскирования ПДн** | Пилот, хакатон, ТЗ без чувствительных данных |

Режим задаётся переменной `LLM_PRIVACY`:

- `auto` (по умолчанию): маскирование включается, если `LLM_BASE_URL` указывает за пределы контура. Внутри контура считаются `localhost`, `127.0.0.1`, `::1`, адреса частных сетей `10.x` / `172.16–31.x` / `192.168.x`, а также имена `*.local`, `*.internal` и `host.docker.internal`.
- `on`: маскировать всегда, даже для локальной модели.
- `off`: не маскировать. Используйте только для заведомо обезличенных ТЗ.

## Что маскируется

Перед каждым запросом к модели система заменяет данные в промпте на плейсхолдеры:

| Данные | Как распознаются | Плейсхолдер |
|---|---|---|
| ИИН | 12 цифр, дата рождения и разряд века правдоподобны, контрольный разряд сходится по алгоритму РК. Если рядом стоит слово «ИИН», достаточно правдоподобной даты (тестовые ИИН в ТЗ часто выдуманы) | `[ИИН_1]` |
| БИН | 12 цифр со структурой БИН и контрольным разрядом, либо со словом «БИН» рядом | `[БИН_1]` |
| Номер карты (PAN) | 13–19 цифр подряд или группами `4-4-4-4`, `4-6-5` через пробел или дефис, с проверкой по алгоритму Луна | `[КАРТА_1]` |
| Телефон | `+7 …` и `8 …` со скобками, пробелами и дефисами | `[ТЕЛ_1]` |
| E-mail | Стандартный формат адреса | `[EMAIL_1]` |
| IBAN | `KZ` и 18 букв или цифр, в том числе группами по 4 | `[IBAN_1]` |
| Организации | Название в кавычках после АО / ТОО / ИП / ООО и т. п., а также «ИП Фамилия И.О.» | `[ОРГ_1]` |

Как устроена замена:

- **Замена обратима.** Таблица «плейсхолдер → значение» хранится только в памяти процесса на время одной проверки. На диск и в логи она не пишется и провайдеру не передаётся.
- **Плейсхолдеры согласованы.** Одно и то же значение во всех агентах заменяется одним плейсхолдером, поэтому модель видит связи («тот же ИИН уходит в аналитику»).
- **Номера строк не сдвигаются.** Маскирование не меняет число строк, поэтому ссылки `L12` в находках указывают на исходный документ.
- **Ответ модели восстанавливается.** В нём плейсхолдеры заменяются обратно до показа пользователю. Цитаты в отчёте совпадают с исходным ТЗ, и верификатор их проверяет.
- **Госорганы и инфраструктура рынка не маскируются.** Например, Национальный Банк, кредитные бюро и биржа: регулятор важен для анализа и не составляет тайны.

## Что никогда не покидает контур

- **Исходный файл ТЗ** (.docx, .pdf, .md). Наружу уходит только текст промпта, а в облачном режиме он замаскирован.
- **Таблица соответствия плейсхолдеров** реальным значениям.
- **Работа офлайн-агентов**: правила, Scorer и верификатор цитат выполняются локально всегда, в любом режиме.
- **Кэш ответов** (`.cache/llm`). Он лежит локально, в облачном режиме содержит только замаскированный текст и отключается через `LLM_CACHE=false`.

## Локальная модель в контуре банка (Ollama)

```bash
ollama pull qwen2.5:14b-instruct
OLLAMA_CONTEXT_LENGTH=32768 ollama serve    # ТЗ до ~80 тыс. символов ≈ 25–30 тыс. токенов
```

```env
LLM_BASE_URL=http://localhost:11434/v1
LLM_API_KEY=ollama          # Ollama ключ не проверяет, но клиент требует непустое значение
LLM_MODEL=qwen2.5:14b-instruct
LLM_MAX_CONCURRENCY=1
LLM_TIMEOUT=600
LLM_CALL_BUDGET=900
```

То же самое можно выбрать в интерфейсе пресетом «Локальная модель (Ollama, контур банка)». Вместо Ollama подойдёт vLLM или любой другой OpenAI-совместимый сервер во внутренней сети.

**Минимальное железо** (ориентир, его нужно проверить на целевом стенде банка):

| Модель | GPU | Без GPU |
|---|---|---|
| `qwen2.5:14b-instruct` (Q4, ~9 ГБ весов) с контекстом 32k | 16 ГБ VRAM, комфортно 24 ГБ (RTX 4090, A10, L4) | 32 ГБ RAM, но один вызов идёт минуты |
| `qwen2.5:7b-instruct` / `llama3.1:8b` (запасной вариант) | 8–12 ГБ VRAM | 16 ГБ RAM |

Модели с 7–8 млрд параметров заметно чаще ломают JSON и пропускают тонкие противоречия. Если модель не справилась, система автоматически переходит на правила, так что результат будет в любом случае.

## Ограничения (честно)

- **ФИО распознаются частично.** Маскируются только ФИО в формате «ИП Фамилия И.О.». Произвольное ФИО в тексте («ответственный — Иванов И.И.»), адреса и номера документов (паспорт, удостоверение) пока не маскируются. Для таких ТЗ используйте локальную модель.
- **Нестандартная запись не распознаётся.** ИИН с пробелами внутри («900101 300 125»), карты с нестандартной группировкой и международные телефоны (не +7) не маскируются.
- **Возможна лишняя маскировка.** 12-значный номер заявки со случайно сошедшейся контрольной суммой будет замаскирован как ИИН. На анализ ТЗ это почти не влияет.
- **Банковская тайна в смысле содержания не скрывается.** Описание бизнес-процессов, лимиты, архитектура и названия внутренних систем остаются в тексте. Если сам смысл ТЗ конфиденциален, подходят только локальная модель или офлайн-правила.
- **Маскирование срабатывает только по шаблонам.** Это не DLP-система. Для промышленной эксплуатации его стоит дополнить DLP банка на шлюзе к внешним API.
